## Contexte

Le design 6C remplace la section perspectives du Reader par deux blocs (CTA court en
haut d'article, section « Analyse des angles » en bas) qui exigent des **constats
attribués** : jusqu'à 3 accords + 2 désaccords, chacun porté par des domaines de médias,
avec un compteur « +N ».

Le backend ne sait produire aucun de ces constats aujourd'hui : `analyze_divergences`
renvoie du **markdown en prose** (§1.3 du plan), redécoupé côté mobile par
`splitAnalysisSections()`. Les médias y sont du gras dans une phrase, pas une donnée.

Mesure prod à l'origine du lot : `perspective_analyses` (la table que le Reader
interroge) contient **0 ligne depuis l'origine**, alors que l'analyse LLM est payée tous
les matins et écrite dans le JSONB `daily_digest`. Le premier gain est un **branchement**,
pas une génération.

## Décisions d'implémentation

### D1 — Une analyse par **sujet**, pas par article

`coverage_analyses` (une ligne / sujet) + `coverage_analysis_articles`
(`(coverage_analysis_id, content_id)`, PK composite, FK `contents(id) ON DELETE CASCADE`).
Le Reader résoudra `content_id → analyse` par jointure directe : ça marche pour **tous**
les points d'entrée (digest, Flux Continu, Veille, Tournée, widget), ce sont les mêmes
lignes `contents`.

Les deux tables sont **backend-only** : RLS activée, `REVOKE ALL FROM anon, authenticated`
(même convention que `sec02_lock_down_new_public_tables`).

`perspective_analyses` est laissée en place et marquée dépréciée dans sa docstring — sa
suppression est un `DROP`, donc un cycle hebdo ultérieur (expand-contract).

### D2 — Un seul appel LLM, sortie structurée **superset** de l'ancienne

`analyze_consensus()` remplace `analyze_divergences()` **au même endroit** (étape 3C).
Son JSON contient les deux clés historiques (`analysis` markdown + `divergence_level`) —
donc `subject.divergence_analysis` continue d'être écrit tel quel et le bloc du digest ne
bouge pas — **plus** les constats structurés (`agreements`, `disagreements`,
`cta_agreement`, `cta_disagreement`).

C'est la seule lecture qui tient la promesse du plan (« le nombre d'appels ne change
pas ») sans casser le digest existant. `max_tokens` passe de 900 à 1400.

`analyze_divergences()` reste en place : elle sert encore
`POST /contents/{id}/perspectives/analyze` jusqu'à la PR 2.

### D3 — Post-traitement déterministe en Python, pas confié au LLM

`normalize_consensus()` (`app/services/editorial/schemas.py`) :

- `support_count = |source_domains ∩ corpus_domains|` — le modèle ne peut pas halluciner
  un « +10 » ;
- **rejet** des constats dont aucun domaine ne recoupe le corpus ;
- troncature **à la phrase** (budget 2 lignes : 130 car. en section, 85 car. dans le CTA —
  dérivés du budget annoncé au modèle dans le prompt, pour que le plafond ne puisse pas
  passer sous lui et tronquer *tous* les constats),
  repli mot + « … » quand la première phrase dépasse déjà le budget ;
- nettoyage du markdown résiduel (`**`), dédup par texte normalisé ;
- tri par `support_count` décroissant (stable) puis plafond **3 accords / 2 désaccords** ;
- CTA : variante courte du LLM si recevable, sinon repli sur le 1ᵉʳ constat re-tronqué au
  budget CTA. Pas de constat dans la section ⇒ pas de CTA : le CTA tease la section,
  il ne vit pas seul.

Les domaines sont donnés au LLM **entre crochets** dans le prompt (`Le Monde
[lemonde.fr]`) et il lui est demandé de ne réutiliser que ceux-là : le filtre par
intersection fait le reste.

### D4 — Qualificatif déterministe

`compute_angle_qualifier(disagreements, bias_by_domain, state=…)` :
0 désaccord → `convergent` ; ≥ 2 désaccords **et** au moins un porté par des biais opposés
(gauche/centre-gauche vs droite/centre-droite) → `polarized` ; sinon → `varied` ;
`state != "available"` → `None` (titre nu : « on ne qualifie pas un débat qu'on n'a pas lu »).

`compute_divergence_level` reste en place, elle sert au ranking.

### D5 — `state` écrit dès la pré-génération

- `available` : au moins un constat recevable après post-traitement ;
- `unavailable` : le gate est passé, l'appel a eu lieu, rien d'exploitable n'en est sorti
  (échec définitif enregistré, pour que la PR 2 ne l'affiche pas éternellement en `pending`) ;
- `pending` : **jamais écrit ici** — c'est l'absence de ligne, dérivée à la lecture (PR 2).

### D6 — Cache de sujet par recouvrement d'articles (mutualisation `pour_vous` / `serein`)

Le `subject_key` est le SHA-1 des `content_id` triés du sujet : il rend l'écriture
**idempotente** sur un re-run, mais il ne dédupliquerait rien entre les deux modes (les
clusters `serein` sont un sous-ensemble filtré, donc un jeu d'articles différent).

Le cache réel est donc un **index `content_id → analyse` en mémoire** porté par
l'instance de pipeline (le job réutilise la même instance pour les deux modes,
`digest_generation_job.py:290`) : si le sujet `serein` partage au moins un article avec
un sujet déjà analysé, on **réutilise la même ligne** `coverage_analyses` (on n'insère que
les liens manquants) et on ne repaie pas l'appel LLM. Log `consensus_cache_hit` pour
mesurer le gain réel en prod.

Effet de bord assumé (et voulu par le plan, D6 « −N appels ») : en mode `serein`, le
markdown `divergence_analysis` réutilisé est celui calculé sur le corpus `pour_vous` du
même événement.

**Limite connue, à traiter en PR 2.** Le cache ne vit que sur l'instance de pipeline.
Le job du matin réutilise la même pour les deux modes (`digest_generation_job.py:274`),
mais `digest_selector.py:419` en construit une **neuve par requête** : un recompute
on-demand (batch raté, redéploiement, première ouverture avant 07h30) repaie les appels
et écrit une **seconde** ligne `coverage_analyses` pour un jeu d'articles voisin — donc
`content_id → analyse` est déjà 1:N. La PR 2 doit résoudre par un `SELECT` sur
`coverage_analysis_articles.content_id` (l'index `ix_coverage_analysis_articles_content_id`
est créé pour ce sens) avec fenêtre de fraîcheur + tie-break sur `generated_at`, le cache
mémoire ne restant qu'un front devant ce lookup. Rien à changer en base : la migration
`ca01` porte déjà l'index.

### Gate 4 → 2

`divergence_llm_min_perspectives` passe à 2 (défaut). C'est déjà un champ `Settings`, donc
`DIVERGENCE_LLM_MIN_PERSPECTIVES=4` sur Railway suffit à revenir en arrière **sans
déploiement**. Coût attendu : +~5 appels/jour (§1.2 : 9 sujets/20 sont aujourd'hui sous le
gate), partiellement compensé par la mutualisation des deux modes.
