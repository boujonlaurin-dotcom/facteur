## Contexte

La PR 1 pré-génère et persiste l'analyse structurée par sujet (`coverage_analyses` +
`coverage_analysis_articles`). Le Reader, lui, ne la sert toujours pas : `GET
/contents/{id}/perspectives` lit encore `perspective_analyses` (0 ligne depuis
l'origine) pour son champ `analysis`, et rien n'expose les constats attribués.

Dette n°1 identifiée en PR 1 (mémoire `project_reader_consensus_6c_pr1`) : le cache
`content_id → analyse` meurt avec l'instance de pipeline, et `digest_selector.py`
construit une instance **neuve par requête** — `content_id → analyse` est donc **déjà
1:N** en base. La résolution Reader doit passer par un `SELECT` sur
`coverage_analysis_articles.content_id` (index `ca01`) avec fenêtre de fraîcheur et
tie-break, pas par le cache mémoire.

## Contrat servi (gelé pour le front 6C)

```jsonc
// GET /contents/{id}/perspectives — ajouts additifs
"consensus": {
  "state": "available" | "pending" | "unavailable",
  "qualifier": "polarized" | "varied" | "convergent" | null,   // null hors available
  "agreements":    [ { "text", "support_count", "display_domains": [..≤2], "plus_count" } ],  // ≤ 3
  "disagreements": [ { ... } ],                                 // ≤ 2
  "cta": { "agreement": {...} | null, "disagreement": {...} | null },
  "generated_at": "…" | null
},
"display": {
  "is_solo":     coverage_count <= 1,
  "has_cta":     coverage_count >= 2,
  "has_cards":   coverage_count >= 2,   // carrousel de couverture
  "has_ai_card": coverage_count >= 3,   // carte IA dans le carrousel
  "has_bar":     coverage_count >= 3    // barre de polarisation
}
```

- `display_domains` : les ≤ 2 domaines à afficher **pour cet utilisateur** (résolus au
  moment de servir, jamais persistés) ; `plus_count = max(0, support_count − 2)`.
- Les gates `display` dérivent du **même** `coverage_count` que « Comparer les N
  angles » et « N médias en parlent » (invariant `coverage_count == len(perspectives)+1`
  intouché).

## Décisions d'implémentation

### R1 — Résolution `content_id → analyse` (dette 1:N de la PR 1)

`app/services/consensus_reader.py` : `SELECT` des lignes `coverage_analyses` liées au
`content_id` (jointure `coverage_analysis_articles`, index `ca01`), fenêtre de
fraîcheur `consensus_reader_freshness_hours` (72 h, env-pilotée), puis choix **en
Python** : `state='available'` d'abord, puis `generated_at` décroissant. Le nombre de
lignes par article est minuscule (1-3) : trancher en Python est testable, la requête
reste simple.

Pourquoi une fenêtre : un article re-clusterisé dans un **nouveau** sujet ne doit pas
servir les constats d'un événement précédent ; 72 h = l'échelle du cycle news (le
lookback digest est 48 h). Trop de `pending` en prod ⇒ bump env sans déploiement.

### R2 — `state` dérivé à la lecture

- ligne fraîche trouvée → son `state` (`available` ou `unavailable`, l'échec définitif
  persisté par la PR 1) ;
- pas de ligne → `pending` si `len(perspectives servies) >= divergence_llm_min_perspectives`
  (c'est le gate réel de génération : « pending » promet qu'une analyse peut exister),
  sinon `unavailable`.

### R3 — Attribution au moment de servir, cache-safe

`_perspectives_cache` est partagé **entre users** (clé = `content_id`) : les picks par
user ne doivent jamais y entrer. Les trois chemins de retour du GET renvoient une
**copie** `{**body, "consensus": …, "display": …}` construite à la requête ; le corps
mis en cache ne porte jamais ces blocs.

Coût par requête : 1 SELECT indexé (analyse) + 2 agrégations en cache —
domaines suivis par user (`user_sources` → domaines, TTL 5 min) et notoriété globale
(`count(user_sources)` par source + `is_curated`, TTL 1 h). Pas de N+1. `source_tier`
explicitement écarté (E8 : faux signal).

Ordre de pick (D3) : suivies d'abord (à égalité, notoriété), puis notoriété
(followers desc, puis `is_curated`, puis ordre corpus — stable). Sur un **désaccord**,
si les candidats couvrent les deux côtés du spectre, on force un domaine de chaque côté
(gauche/centre-gauche vs droite/centre-droite). Le biais par domaine vient du corpus
servi (`perspectives[].bias_stance`) ; un domaine du constat absent des alternatives est
le pivot → `source_bias_stance`.

Dégradé : toute erreur DB sur ce chemin sert `consensus` dérivé sans ligne (R2) et ne
fait jamais tomber la réponse (même motif que `_attach_deep_from_store`).

### R4 — POST `/analyze` : write-through + budget

Flow conservé (L1 mémoire → L2 `perspective_analyses` → génération), avec trois
changements :

1. **Garde-fou de budget quotidien** avant l'appel LLM : `daily_call_count("mistral",
   call_site="reader_consensus")` ≥ `consensus_lazy_daily_cap` (30, env-piloté) →
   réponse `{analysis: null, throttled: true}` **non cachée** (retente à la fenêtre
   suivante). Compteur persistant sur `api_usage_events` (survit aux restarts, même
   motif que le cap mensuel PR-S3).
2. **`analyze_consensus` remplace `analyze_divergences`**, avec
   `call_site="reader_consensus"` (distinct de `editorial` : le chemin paresseux se
   mesure et se plafonne seul). Le markdown `analysis` du JSON superset alimente la
   réponse legacy + `perspective_analyses` (inchangé pour le parc installé).
3. **Write-through** : `normalize_consensus` sur le corpus servi (pivot + alternatives),
   upsert `coverage_analyses` (même `subject_key` = signature des `content_id` connus)
   + liens. Les articles Google News sans `content_id` ne produisent pas de lien —
   attendu, ils n'existent pas dans `contents`.

L'upsert et l'insertion des liens sont **extraits** de `pipeline.py` vers
`consensus_reader.py` (une seule copie du SQL) ; le pipeline délègue, comportement
inchangé.

### R5 — Ce qui ne change pas

- `analysis` / `analysis_cached` / `divergence_level` / `should_display` /
  `comparison_quality` : mêmes sources de données qu'avant.
- L'invariant `coverage_count == len(perspectives) + 1` (script QA existant).
- Le prompt : `analyze_consensus` est appelé tel quel, seul `call_site` (nouveau
  paramètre, défaut `editorial`) change sur le chemin paresseux.
