# Story 31.1 — Onboarding sans compte (session anonyme Supabase)

**Epic 31 — Activation & réactivation**
**Type** : Feature
**Statut** : en cours

---

## Problème

Funnel prod 90 j (130 installs, 100 % Android) : **37 % seulement des installs créent un compte**.
82 installs sur 130 (63 %) n'émettent aucun event produit : installée, ouverte, backgroundée, fin.
Médiane 9 events, 162 secondes, 1 seul jour d'activité, **0 % de rétention à J1, J7 et J30**.

En face, les 48 activés se rétiennent très bien (J7 77 %, J30 67 %) et l'onboarding lui-même se
termine à 91 % (114/125). Le produit ne perd pas ses utilisateurs à l'usage, il les perd **avant**
l'usage.

Cause directe : `apps/mobile/lib/config/routes.dart` (garde 1) renvoie tout nouvel install
**directement sur `/login`**. Zéro exposition produit avant de devoir créer un compte, puis
confirmer son email.

## Objectif

Activation install → compte : **37 % → 60 %** à 6 semaines. C'est le seul chiffre qui compte.
Objectif secondaire : rendre le funnel d'onboarding lisible (aujourd'hui une seule étape sur 13
émet un event).

---

## Approche : session anonyme Supabase, convertie à `finalize`

Deux options :

- **(a)** bufferiser toutes les réponses en local et rendre publics les endpoints nécessaires ;
- **(b)** ouvrir une session **anonyme** Supabase au premier lancement et la convertir en compte à
  `finalize`.

**Retenu : (b).** Les étapes `sources`, `swipe` et `subtopics` consomment déjà des endpoints
authentifiés (`userSourcesProvider`, `sourceProfileProvider`, `customTopicsProvider` ; tout
`routers/sources.py` est derrière `get_current_user_id`). L'option (a) obligerait à dupliquer ces
endpoints en version publique et à réécrire le chemin d'écriture. L'option (b) donne un vrai JWT dès
la première seconde : **aucun endpoint ne change, aucun buffer à écrire**, et à la conversion
Supabase conserve le même `user.id` — donc profil, sources et thèmes déjà écrits restent attachés.

`supabase_flutter ^2.5.0` / `gotrue 2.18.0` exposent `signInAnonymously()` et `User.isAnonymous` ;
`auth.users.is_anonymous` existe déjà en base.

### Cycle de vie d'une session anonyme

```
cold boot, pas de session, auto-signin autorisé
  └─> signInAnonymously()          user.is_anonymous = true, pas d'email
       └─> onboarding complet       profil + sources + thèmes écrits sous cet id
            └─> finalize : updateUser(password) puis updateUser(email)
                 └─> pendingEmailConfirmation posé ET persisté (Hive auth_prefs)
                      └─> /emailConfirmation → clic dans l'email
                           └─> is_anonymous = false, email_confirmed_at posé
```

`is_anonymous` **reste `true`** entre la conversion et la confirmation de l'email : c'est Supabase
qui le bascule à la confirmation. Le pivot côté client est donc `pendingEmailConfirmation`, pas
`isAnonymous` — et il doit survivre à un kill/relaunch, d'où sa persistance Hive.

### Garde-fou anti-boucle

L'auto-signin anonyme ne se déclenche qu'au **cold boot**, et jamais sur un appareil qui a déjà vu
un vrai compte : une clé `auth_prefs.anon_auto_signin_disabled` est posée dès qu'un utilisateur non
anonyme est observé (`_noteRealAccount`, appelé au boot et depuis le listener Supabase) ainsi qu'au
`signOut`. Se contenter des chemins explicites (email, conversion, déconnexion) laisserait passer un
login OAuth ou une session simplement expirée : l'utilisateur historique se réveillerait dans un
onboarding anonyme vierge au lieu de son écran de connexion.

## Tâches

### Mobile

- [x] `core/auth/auth_state.dart`
  - `AuthState.isAnonymous` (dérivé de `user.isAnonymous`).
  - `pendingEmailConfirmation` persisté / restauré dans la box Hive `auth_prefs`.
  - `_maybeStartAnonymousSession()` appelé depuis `_init()` quand aucune session n'existe et que
    l'auto-signin n'est pas désactivé. Échec ⇒ on retombe sur `/login` (dégradation propre).
  - `convertAnonymousToAccount()` : `updateUser(password)` puis `updateUser(email)` sur la session
    anonyme, puis `pendingEmailConfirmation`. **Ne vide aucune box** (contrairement à `signOut`).
  - `_checkOnboardingStatus()` : chemin rapide pour un anonyme sans profil ⇒ `needsOnboarding = true`,
    `onboardingStatusKnown = true`, sans attendre la DB (le splash ne bloque pas).
- [x] `config/routes.dart`
  - Garde 2 (`!isEmailConfirmed` ⇒ `/emailConfirmation`) : exemptée pour une session anonyme **sans**
    conversion en attente. Gardes 2b (splash / FLUTTER-2), 5 et 6 (gate Rituel, deep links) intactes.
- [x] `features/onboarding/screens/questions/finalize_question.dart` : accueille la création de
  compte (email + mot de passe, ou « J'ai déjà un compte »). L'écran de résumé reste tel quel pour
  un utilisateur déjà authentifié qui refait son onboarding.
- [x] `features/onboarding/onboarding_strings.dart` : copy de l'étape compte (tutoiement, métaphore
  postale, zéro em-dash).
- [x] `main.dart` : ne PAS `$identify` (ni login RevenueCat) sur une session anonyme, sinon la
  métrique d'activation install → compte devient mécaniquement 100 %. `is_anonymous` ne retombant
  qu'à la confirmation de l'adresse, un event **`account_created`** est émis à la conversion (et sur
  le chemin classique `signUpWithEmail`) : c'est lui, et non `$identify`, qui porte désormais la
  mesure d'activation. Comparable à la baseline, qui comptait le signup, pas la confirmation.
- [x] **Instrumentation** : `features/onboarding/providers/onboarding_analytics.dart` — un listener
  branché sur `onboardingProvider` émet `onboarding_started`, `onboarding_step_viewed` et
  `onboarding_step_completed` (avec `step_name` + `step_index`) sur les 13 étapes, plus
  `onboarding_completed` à la conversion. Sans ça les 63 % restent indiagnosticables.

### Backend

- [x] `app/dependencies.py` : la garde email rejette les anonymes (`email_confirmed_at` nul).
  Accepter sur le claim JWT `is_anonymous`, et étendre le fallback DB en
  `SELECT email_confirmed_at, is_anonymous`. Le cache positif TTL 1 h ne nécessite pas
  d'invalidation : il n'encode qu'un « autorisé », et la conversion anonyme → confirmé ne fait
  qu'élargir l'accès.
- [x] `app/jobs/purge_anonymous_users.py` + `add_job` dans `app/workers/scheduler.py`
  (`max_instances=1`, `coalesce=True`, 4h15 Paris) : supprime les users anonymes dont l'onboarding
  n'a pas abouti et inactifs > 30 j, sinon `auth.users` enfle d'une ligne par install. Sélection en
  SQL, suppression via l'Admin API Supabase (le rôle applicatif n'a que le SELECT sur `auth.users`)
  puis `DELETE` du profil applicatif (CASCADE), plafond 500/run.
- [x] `app/services/user_service.py` : inchangé. Le profil est créé sous l'id anonyme et survit à la
  conversion.

> **Le critère de purge n'est PAS « aucun profil ».** Les endpoints d'onboarding
> (`custom_topics`, `personalization`, `notification_preferences`) appellent déjà
> `get_or_create_profile` — c'est ce qui rend l'approche viable, puisque `user_subtopics` et
> `user_interests` portent une FK sur `user_profiles.user_id` : sans ce profil créé à la volée, la
> première sauvegarde de sous-sujet exploserait en violation de FK. Corollaire : un profil existe
> souvent bien avant la fin du parcours, donc seul `onboarding_completed = false` distingue un
> abandon d'un utilisateur réel.

## Risques

| Risque | Mitigation |
|---|---|
| Une ligne `auth.users` par install (abus / volume) | Job de purge 30 j + rate limit Supabase sur les anonymous sign-ins |
| Perte de données à la conversion | Même `user.id` conservé par Supabase ; testé explicitement (thèmes, sous-sujets, sources) |
| Fenêtre email non confirmé après conversion | Voulu : la garde reprend et renvoie vers `/emailConfirmation`. La copy de l'écran reflète que tout est déjà configuré |
| App tuée entre conversion et confirmation | `pendingEmailConfirmation` persisté en Hive et restauré au boot |
| Utilisateur déconnecté re-basculé en anonyme | `anon_auto_signin_disabled` posé à tout choix d'auth explicite |
| Widget tests montant le router / `authStateProvider` | Baseline mobile connue : ~27 échecs préexistants, à ne pas confondre avec des régressions |

## Vérification

1. `cd packages/api && pytest -v` ; `cd apps/mobile && flutter test && flutter analyze`.
2. Alembic : 1 seul head (cette PR **n'ajoute aucune migration**).
3. Parcours complet Playwright sur le build web : premier lancement sans compte → 13 étapes →
   création du compte à `finalize` → thèmes / sous-sujets / sources choisis *avant* le compte
   présents après.
4. Edge cases : back au milieu de l'onboarding puis kill/relaunch ; « J'ai déjà un compte » depuis
   `finalize` ; conversion avec un email déjà utilisé ; app tuée entre conversion et confirmation.
5. En base : `select is_anonymous, count(*) from auth.users group by 1` ; le profil porte le même
   `user_id` avant et après conversion.
6. PostHog : `onboarding_step_viewed` arrive avec les bons `step_index`.

**Mesure de succès (6 semaines)** : install → `account_created` de 37 % à 60 % (la baseline 37 %
était mesurée sur `$identify`, qui partait au signup ; `account_created` marque le même moment), et
apparition d'un funnel d'étapes exploitable dans PostHog.
