## Contexte

La PR #1 a posé les fondations serveur : gouverneur de budget push
(`push_governor.py`) et push quotidien « coup d'œil » (`push_composer.py`).

Cette story livre le **premier vrai geste utilisateur** de l'epic : poser une
cloche sur une source rare. C'est le cas d'usage le plus sûr — impossible à
transformer en spam par construction (source < 1 article/semaine, plafond 5
cloches) — et il installe le geste « poser une alerte » dont dépend la PR #3
(alerte sujet, qui ne se lance que sur preuve d'usage de celle-ci).

Philosophie validée : **une info = une notif claire ; séparation dans
l'affichage, groupement dans le temps**. L'alerte est une notification
distincte, silencieuse, livrée au créneau de l'utilisateur. Seule la tournée
sonne.

Deux nettoyages sont embarqués à la demande du PO : un bouton QA pour tester la
notif sur téléphone avant merge, et la suppression complète de la notif hebdo
« Les Fact·eur·isses adorent cet article » (bruit inutile).

## Arbitrages PO (tranchés le 26/07/2026)

1. **Cloche vs règle 4h du gouverneur** — contradiction réelle :
   `check_push_budget` refuse tout kind non rituel à moins de 4h d'un rituel
   envoyé/à venir, donc *toute* alerte serait refusée. **Décision : exempter les
   alertes du cooldown rituel** (`ritual_companion=True`), les budgets 2/24h et
   6/7j restent appliqués. L'alerte est silencieuse et part dans la même passe
   que la tournée.
2. **`NotifPreset.curieux`** — la pépite hebdo était sa *seule* différence avec
   `minimaliste` (le backend stocke `preset` sans jamais le lire). **Décision :
   le sélecteur de préset est remplacé par le réglage des Alertes.**
3. **Découpage** — une seule PR.
4. **Bouton de test** — injection locale du payload exact dans le handler
   client (testable depuis l'APK de la branche, sans backend).

## Écart constaté vs plan initial

Le plan supposait `es01_essentiel_placement` comme head Alembic unique. Au
moment de l'implémentation, `origin/main` porte **deux heads** issus d'un merge
concurrent (`pt01_contents_entities_trgm` et `rd01_ucs_completed_at`, tous deux
enfants de `181c618da382`) — cas déjà rencontré (cf. `mg01`/`mg02`/`mg03`). La
story ajoute donc une révision de merge vide `mg04_merge_pt01_rd01` avant sa
propre migration, conformément à la convention du repo (1 seul head exigé par
le hook `post-edit-alembic-heads.sh` et par `alembic upgrade head` au boot
Railway).

## Backend (`packages/api`)

### 1. Migrations

- `alembic/versions/mg04_merge_pt01_rd01.py` — révision de merge vide,
  `down_revision = ("pt01_contents_entities_trgm", "rd01_ucs_completed_at")`.
- `alembic/versions/sa01_user_sources_notify.py`,
  `down_revision = "mg04_merge_pt01_rd01"` :
  - `ALTER TABLE user_sources ADD COLUMN notify BOOLEAN NULL` — **nullable**,
    comme le précédent `essentiel_mode` : strictement additif, aucun risque pour
    le backend `production` qui tourne sur la DB partagée (règle
    expand-contract). Lu partout comme `notify IS TRUE`.
  - Index partiel
    `ix_user_sources_notify_source ON user_sources (source_id) WHERE notify IS TRUE`
    (le producteur part des contenus récents et remonte vers les abonnés).
  - `downgrade` : drop index + colonne. Migration idempotente.

Modèle : `app/models/source.py` → `UserSource.notify: Mapped[bool | None]`.

### 2. Éligibilité « source rare » — source de vérité partagée

`app/services/source_alert_producer.py` (nouveau) expose une fonction pure :

```python
def is_rare_source(articles_30d: int, oldest_content_at: datetime | None, now: datetime) -> bool
```

Même logique de fenêtre bornée que le mobile (`publication_frequency.dart`) :
fenêtre 30 j clampée à l'âge réel de la source (1..30 j) pour ne pas classer
« rare » une source qui vient d'être ingérée. Rare ⇔ `articles_30d >= 1` **et**
`perDay * 7 < 1`. Le `articles_30d == 0` n'est **pas** éligible : pas de preuve
qu'elle publie (source morte ou flux cassé), la cloche ne sonnerait jamais.

Ce test est rejoué côté serveur à l'activation **et** au dispatch (défense en
profondeur : le client peut avoir un profil périmé).

### 3. `kind` par alerte — sans toucher `push_deliveries`

`push_deliveries` a `UniqueConstraint(device_id, target_date, kind)`. Si toutes
les alertes d'un jour partageaient `kind = "source_alert"`, deux cloches
déclenchées le même jour entreraient en collision. Modifier la contrainte n'est
pas expand-contract safe.

Solution sans migration : **le `kind` porte la source**,
`source_alert:{source_id.hex[:16]}` = 29 caractères, tient dans `String(32)`.
Helpers : `source_alert_kind(source_id)` / `is_source_alert_kind(kind)`.
Le gouverneur traite ces kinds comme non-rituels (test d'appartenance exact à
`RITUAL_KINDS`) et les compte chacun comme 1 push contre les budgets.
Analytics et PostHog reçoivent le `kind` propre `source_alert` + une propriété
`source_id`.

### 4. Gouverneur — exemption du cooldown rituel

`app/services/push_governor.py` : nouveau paramètre
`ritual_companion: bool = False` sur `check_push_budget`. Quand `True`, les
branches `ritual_cooldown` / `ritual_upcoming` sont sautées ; les budgets
journalier et hebdomadaire restent appliqués tels quels.

Conséquence assumée : le budget de 2 push/24h étant partagé avec la tournée,
**au plus 1 alerte par jour** passe ; les suivantes sont `skipped` avec
`daily_budget_exceeded`. C'est le garde-fou qui fait son travail, pas un bug.

`next_ritual_at` (aujourd'hui sans appelant de production) reste en place pour
la PR #3.

### 5. Producteur + dispatch

`app/services/source_alert_producer.py` :
`find_source_alert_candidates(session, *, user_id, now)` —
`DISTINCT ON (source_id)` sur `contents` publiés dans les 24 h, joints aux
`user_sources` avec `notify IS TRUE` et `state IN FOLLOWED_SOURCE_STATES`,
filtrés par `is_rare_source`.

`app/services/push_composer.py` : `compose_source_alert(...) -> ComposedPush`
- titre `📯 Alerte : {source} vient de publier`
- body = titre de l'article, tronqué via `_truncate_fact` (90 c, coupe au mot)
- bigText = body + ligne de rareté dérivée des mêmes seuils que `is_rare_source`
- `data = {route: /article/<id>, kind: source_alert, source_id, content_id, channel: alerts}`

`app/services/push_alert_dispatcher.py` (nouveau) :
`dispatch_source_alerts(*, now, sender)`. Réutilise les helpers de
`push_dispatcher.py` rendus publics (`is_due`, `get_or_create_delivery`,
`send_fcm`) plutôt que de les dupliquer. Même garde Firebase, même
`ON CONFLICT DO NOTHING`, même passage par le gouverneur
(`ritual_companion=True`), mêmes métriques.

`app/workers/scheduler.py` : job `source_alert_push_dispatch`,
`IntervalTrigger(minutes=5)`, `coalesce=True`, `max_instances=1`, ajouté à la
liste littérale du `logger.info("Scheduler started", jobs=[...])`.

### 6. Endpoints

Dans `app/routers/sources.py` (à côté de `/trust`, mêmes invalidations de cache) :

- `PUT /api/sources/{source_id}/alert` — body `{enabled: bool}` →
  `{enabled, active_count, cap}`. Refus : 404 source inconnue, 409
  `not_followed`, 409 `alert_cap_reached` (5), 422 `source_not_rare`.
  Désactiver est toujours autorisé (pas de vérif de rareté).
- `GET /api/alerts` → `{cap, active_count, items: [...]}` avec par item :
  `source_id`, `source_name`, `source_logo_url`, `articles_30d`,
  `last_published_at`, `last_alert_sent_at` (max `push_deliveries.sent_at` sur
  le kind composite), `new_content` (contenus < 24 h non lus). Alimente l'écran
  « Mes alertes » (« silence comme preuve » = `last_published_at`) **et** la
  section Tournée.
