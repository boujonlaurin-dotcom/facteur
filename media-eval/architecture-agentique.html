Architecture agentique d'évaluation des médias

Comment Facteur évalue la fiabilité d'un média sur 11 critères (100 points) grâce à un pipeline qui sépare strictement la collecte de signaux de leur évaluation par des sous-agents, avec un score toujours dérivé par code, jamais choisi librement par un modèle.

1 Le principe fondateur : collecte ≠ évaluation

Deux phases, un data store entre les deux. La collecte produit des observations factuelles, la collecte ne note jamais. L'évaluation lit uniquement ces observations, l'évaluation ne collecte jamais.

Phase COLLECTE

Produit des signaux : observations factuelles avec source, URL, date, citation et capture horodatée (snapshot). Chère (fetch, navigation, lecture) donc tourne une fois.

  • Statuts distincts : present, absent_verifie, partiel, bloque_acces.
  • « Absence vérifiée » et « bloqué » sont tracés, pas confondus avec un échec.

Phase ÉVALUATION

Un sous-agent par critère, sans accès web, ne lit que les signaux d'un couple (média, critère) + le barème verbatim. Bon marché (lecture de JSON) donc peut tourner N fois.

  • Rend des déterminations énumérables, jamais un score chiffré.
  • Chaque affirmation cite des signal_ids précis.
Quatre garanties alignées sur la méthodo : reproductibilité (re-noter sans re-collecter, indispensable au contradictoire), traçabilité (chaque point cite ses signaux), auditabilité du non-collecté (absence vérifiée vs accès bloqué), coût maîtrisé (collecte une fois, évaluation N fois).

2 Le pipeline macro

Le flux complet d'un run, du référentiel média à la fiche publiée. Les agents collecteurs et les agents évaluateurs sont des rôles distincts : jamais le même agent cherche et note.

1

Référentiel média CODE

seed_medias.py → domaine, type (presse en ligne / audiovisuel), volume/jour, paywall. Conditionne échantillons et routage.

2

Collecte, 3 voies en parallèle CODE AGENT HUMAIN

Voie A : collect_*.py écrit en DB. Voie B : agents Claude → artefacts JSON dans .context/media_eval/<run_id>/, jamais d'écriture DB directe. Voie C : humain (paywall, golden set). Sortie unique : des signaux horodatés + snapshots. Zéro notation.

3

Ingestion & data store CODE

ingest_artifacts.py valide les artefacts agents (Pydantic strict) puis insère signaux + débunkages. Rejet en bloc si un artefact est invalide : rien n'est écrit.

4

Construction de l'entrée d'évaluation CODE

build_eval_input.py → eval_inputs/<media>_<critere>.json : signaux + barème verbatim. Applique les garde-fous amont (fraîcheur, raccourci JTI, déclencheur fallback C1) et calcule version_prompt = sha256 de la rubrique.

5

Évaluation par sous-agents AGENT

1 agent par critère, sans accès web → evaluations_<media>_<critere>.json : déterminations + justification + signal_ids_cites. Aucun score chiffré.

6

Ingestion des évaluations CODE

ingest_evaluations.py applique les garde-fous aval (signal_ids valides / bon média / bon critère, corroboration, bloque_acces → revue) puis dérive le score par code.

7

Synthèse de la fiche CODE

synthese_fiche.py renormalise sur les critères applicables (règle de trois), attribue la lettre A–E et le niveau de confiance (haute / moyenne / basse).

8

Mesure d'accord vs golden set HUMAIN CODE

evaluate_golden_agreement.py compare la sortie du harness à la notation humaine de référence. On ne publie rien tant que l'accord n'est pas stable.

3 Les trois voies de collecte

Règle de routage : le code pour le déterministe, l'agent pour le jugement, l'humain pour l'inaccessible et le contradictoire. Un signal descend toujours au niveau le plus bas (le moins cher) capable de le produire de façon fiable.

VOIE A · CODE

Scripts + edge functions planifiables. Déterministe, répétable, quasi gratuit.

  • Crawl structurel (mentions légales, chartes, corrections, publicité) + snapshots.
  • Registres : Pappers, CPPAP, JTI, avis CDJM.
  • Constitution du corpus (échantillonnage stratifié documenté).
  • Pré-métriques d'articles (bylines, labels, liens).

VOIE B · AGENT

Sous-agents Claude avec accès web (dont fetch navigateur). Lecture, recherche ouverte, qualification. N'écrivent jamais en DB.

  • Recherche ouverte : débunkages, condamnations, départs, déclarations.
  • Qualification : pondérer un débunkage, juger une charte.
  • Analyse de corpus (vague 2) : sourçage, cadrage, diversité.
  • Extraction structurée (page « Qui sommes-nous » → données).

VOIE C · HUMAIN

Rare et ciblé : là où ni le code ni l'agent ne peuvent aller, ou là où la méthodo exige un regard second.

  • Corpus paywallé (copie manuelle déposée, puis analyse en voie B).
  • Double évaluation C9 / C11, divergences documentées.
  • Contreseing du fallback C1 avant entrée au score.
  • Golden set de calibration.
Répartition observée sur les ~40 signaux de la grille : environ 40 % collectables par code, 45 % par agents, 15 % exigent l'humain. Le point de rupture identifié au batch-test #1 (27/06/2026) n'est pas l'intelligence mais l'accès (blocklist, paywalls) et la disponibilité (zéro donnée tierce sur les médias de niche). L'accès est donc traité comme une propriété du signal (statut dédié), pas comme un échec de collecte.

4 Le data store (tables media_eval_*)

Tout ce que la fiche publiée doit contenir (source, URL, date, citation) est un champ obligatoire dès la collecte, pas une reconstruction a posteriori. RLS deny-all sur toutes les tables (outillage interne).

TableGrainRôle
mediasdomaine / médiaRéférentiel : type presse en ligne / audiovisuel, volume/jour, paywall, rubriques d'opinion. Distinct de sources (grain feed RSS de l'app live).
snapshotspageCapture horodatée + hash d'une page type (mentions légales, charte, corrections). Preuve, gère les incohérences internes.
corpus_articlesarticleÉchantillon délibéré et figé (stratifié rubrique × mois), texte stable, pré-métriques. Vide en V0.
signauxobservationLa table pivot. media_id, critere, type_signal, statut, valeur (jsonb + citation), voie, collecteur, source_urls, snapshot_id, sources_consultees.
debunkagesdébunkageemetteur + poids_emetteur (dérivé par code), gravité, suite donnée. Alimente le signal C1.
evaluations(média, critère)score, niveau, justification, signal_ids cités, évaluateur (agent / humain), version_methodo, version_prompt, evalue_at.
fichesmédiascore brut, score renormalisé, lettre, critères N/A, confiance, statut (brouillon / contradictoire / publiée).

Articulation avec l'app. media_eval_* est le système d'audit versionné ; les colonnes plates de sources (reliability_score…) sont un cache applicatif. À terme, les fiches pourront alimenter ces colonnes par projection. Ce n'est pas un doublon : un média = N sources.

5 Le harness d'évaluation par sous-agents

Un contrat d'entrée / sortie strict, verrouillé par validation programmatique. L'agent produit du jugement énumérable ; le code produit le score.

Entrée

  • Les signaux du data store pour un couple (média, critère).
  • Le barème §4 du critère, lu verbatim.
  • D'éventuels pre_flags posés par les garde-fous amont.
  • Aucun accès web, fichier ou base. Signal manquant → l'agent le dit, il ne va pas le chercher.

Sortie

JSON structuré evaluations_<media>_<critere>.json :

  • determinations : valeurs énumérées par la rubrique (rien d'autre).
  • justification : 2 à 6 phrases, chacune adossée à des signal_ids.
  • signal_ids_cites : non vide, sauf N/A.
  • flags : dans le contrat uniquement.
  • Pas de champ score : rejet à la validation.

Les flags autorisés et leur effet (appliqué par code)

FlagSensEffet
donnees_insuffisantesSignaux insuffisants pour appliquer le barèmeCritère N/A, exclu de la renormalisation
signaux_contradictoiresLes signaux se contredisentScore partiel + justification ; confiance dégradée
bloque_accesSeuls signaux pertinents = accès bloquéRevue requise, jamais converti en 0
revue_humaine_requiseCas limite signalé par l'agentConfiance basse sur la fiche
Le score faisant foi est dérivé par code (derive_score), depuis les determinations énumérables, jamais choisi librement par le modèle. Même philosophie que derive_reliability pour les sources. La validation Pydantic rejette en bloc un artefact non conforme : le rejet devient un feedback loop, pas un piège.

6 Les garde-fous, codés en dur (jamais dans les prompts)

Toute règle mécanique de la méthodo sort du prompt et devient une validation programmatique. Deux moments : amont (avant l'agent, dans build_eval_input.py) et aval (après l'agent, dans ingest_evaluations.py).

Amont · build_eval_input.py

  • Fraîcheur : signal événementiel > 730 jours → exclu (N/A automatique).
  • Raccourci JTI : certification valide → C8 plein, sans passage par l'agent.
  • Déclencheur fallback C1 : < 3 débunkages / 2 ans → pre_flag fallback_c1_declenche.
  • Neutralité ARCOM : presse en ligne → signaux ARCOM exclus (N/A structurel neutre).

Aval · ingest_evaluations.py

  • Intégrité des citations : chaque signal_id doit exister, bon média, bon critère.
  • Corroboration : ≥ 2 sources indépendantes pour un score plein, sinon plafonné au palier inférieur.
  • Bloqué ≠ zéro : bloque_acces → revue requise, jamais 0.
  • Score dérivé par code depuis les déterminations.

Synthèse (pur calcul) : renormalisation sur 100 (règle de trois sur les critères évaluables), lettre A–E, niveau de confiance HAUTE / MOYENNE / BASSE. Une confiance BASSE n'est pas publiable.

8 Calibration & confiance

On ne fait pas confiance au harness par principe : on le mesure contre un golden set humain avant toute évaluation en série.

Golden set

Notation humaine de référence (Laurin), critère par critère. Chaque version du harness (prompt ou modèle) est mesurée contre ce set : accord exact sur les échelles à 3 niveaux (C9, C11), écart toléré sur les échelles continues.

Puis QA en continu

Une fois l'accord stable : QA humaine en échantillonnage (1 fiche sur N revue intégralement) + double évaluation systématique C9 / C11. Rien n'est publié tant que l'accord agent/humain n'est pas stable.

Critères de succès V0 : 100 % des artefacts évaluateurs passent la validation sans édition manuelle · accord vs golden sur ≥ 4 critères / 6 par média · Reporterre sort C1 en N/A donnees_insuffisantes (pas 0) et renormalise sur 34 pts · zéro écriture DB par agent (par construction).

9 Périmètre V0 & phasage

Vague 1 : le socle structurel

Scorable dès maintenant : C5, C7, C8, C9, C11 (manifeste) + C1 (données tierces). Collecte code + agents sur pages du média et registres ouverts. Homogène sur tous les médias, petits inclus. Budget : ~25-30 appels d'outils web et 5-10 min d'agent par média.

Médias pilotes : CNEWS (audiovisuel, ARCOM applicable) et Reporterre (presse en ligne de niche, teste donnees_insuffisantes + renormalisation avec N/A).

Vague 2 : les critères article-dépendants

C2, C4, C6, C10 + C1 (fallback) + C11 (cadrage). Prérequis : fetch navigateur + stratégie paywall + échantillonneur stratifié. À lancer sur 2-3 médias pilotes avant d'industrialiser.

Hors scope V0 : corpus d'articles (table créée, vide), paywall, procédure contradictoire, UI/API, lien avec sources.reliability_score, scheduling, multi-évaluateurs, SDK Anthropic.
